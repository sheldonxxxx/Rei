# Composer context

The composer’s **+** button and a word-boundary **@** open one searchable picker. It accepts attachments, configured MCP connectors, and chats across all agents. Connector and chat mentions retain IDs independently of their display labels. Selecting a connector adds its tool directory to the message: one line per tool this conversation registered for it, the same listing a connector-only `search_capabilities` query returns, with a note to load the tools needed by name. Nothing is loaded, no permission is granted and no other tool is hidden; calls still go through policy. The picker shows when a connector is unavailable for new mentions. An existing mention can still list its previously discovered tools during a connection error, and Rei checks the live definition before using one. When the agent lacks access, the connector needs sign-in, or its tools could not be discovered, the mention tells the model why the tools are unavailable. The server refuses only a connector that no longer exists. A mentioned chat is read on demand with `read_chat`, without granting worker-management access.

In the `/` palette and the `@` picker, **Tab** completes the highlighted row: a skill becomes a chip, a connector, chat or page becomes a mention, and `/compact` is filled in without running. As you type, the highlight goes to the best match: a name that starts with the query, then a later word of a name (`sum` finds `acme/summarize`), then any other part of a name, then a description. Disabled rows are passed over. With nothing to complete, and for **Shift+Tab** and the **+** menu, Tab moves the focus as usual.

Pasting more than 4,000 Unicode code points creates a UTF-8 `pasted-text-YYYYMMDD-HHmmss.txt` attachment. The file preserves original whitespace and line endings. The existing draft stays intact. Clipboard files take precedence over accompanying text. Failed or rejected generated files retain **Retry upload**, **Insert as text**, and removal controls. Text inserted into the native editor uses LF line endings. File names receive a numeric suffix for repeated pastes within a second.

## Slash commands and selected skills

Typing `/` as the first word of the draft opens a palette with Rei's built-in **slash commands** and the skills the session's agent can use. It never opens inside a sentence, for a path later in the line, in code, while an IME is composing, or once the caret leaves the first word. **Escape** closes it without changing the draft; arrow keys move, **Tab**, **Enter**, click or touch picks, and an Enter with nothing to pick sends the text as it is. Skills show their size; a skill already chosen, or any skill once five are chosen, is greyed out. The list is fetched from the session's own agent each time it opens (`GET /api/sessions/:id/skills`: id, display name, description, current version, `bodyChars`; no instructions or file bytes).

- **Choosing a skill** removes only the `/word` and adds a removable chip for the next message. The chip is pinned to the version seen at the draft's latest refresh and is re-checked when the draft is restored (a gone skill stays visible as unavailable and blocks Send until removed). Chips alone are not a message: Send stays off with the reason shown. The draft, mentions and files are untouched.
- **Sending** posts `selectedSkills: [{ id, version }]` (at most five, no repeats, in chip order) with the message. Admission is all-or-nothing and checks the skill before anything is admitted: `409 skill_unavailable`, `400 too_many_skills`, `413 skills_too_large` (the instructions alone would not fit the model's context window). A rejected send keeps the draft and the chips and shows the reason; the same draft keeps one `requestId`, so a resend after a lost reply is one message. A retry of an already-admitted request is answered before any availability check. There is no per-message total cap; one skill's `SKILL.md` may be up to 200,000 characters.
- **The model's input** starts with one `<selected-skill name version id>` block per chip (the exact version's instructions, with a note that it grants nothing), then the message text, then `[Selected context]`. Supporting files are copied to `.skills/<id>/v<N>/<runId>/` of the sandbox; with no sandbox, or on a copy failure, the block says so and the files stay readable with `read_skill_file({ id, version, path })`, which reads that exact version. Nothing is run because a skill was selected, and every tool call is still decided by the policy. Selecting a skill is not `use_skill`, which stays available to the model.
- An admitted message keeps the skill versions it was sent with. Disabling or removing a skill or its plugin blocks new selections and live tool calls. The message shows its skill chips, and Edit lets you remove them. Rei checks the skills you keep before rewinding the chat. [ADR 0006](adr/0006-admitted-input-freezes-selected-skills.md)
- **Trace and context.** In detail mode the Trace shows the full prepared input, and the context breakdown counts each block under _Skills_ as `Selected skill: <name>` and the user's own text under _Conversation_. Service logs carry skill ids only.
- **`/compact [guidance]`** is the only built-in command. A skill is never a command, and a skill named `compact` is chosen from the list, never by typing. Picked from the list, or completed with Tab, it fills `/compact ` so guidance can follow; typed in full it runs on Enter or Send and clears only the command text (files and chips stay). Guidance is at most 4,000 characters (`413 too_long`).

### Manual compaction

`POST /api/sessions/:id/compact` with `{ requestId, instructions? }` asks Pi Durable's native `Conversation.compact()` for a summary. It is not a message and starts no run, and it works with automatic compaction turned off. The answer is _accepted_, never _done_: `GET /api/sessions/:id/compact/:requestId` and the session view's `live.manualCompaction` report `accepted`, `running`, `pending_placement`, `applied`, `no_change`, `stale`, `failed` or `unknown_after_restart`.

- A finished task is not a visible compaction. If it produced a write submission, only a `done` submission is `applied` (the compaction marker is in the transcript); an `unanswered` one is `stale`; a queued one is `pending_placement`. A task with nothing to cut ends `no_change`. Every ending other than `applied` leaves a notice line in the transcript.
- Rei writes a `manual_compactions` row as its intent (idempotent by `requestId`), calls Pi, then links the task id. Pi takes no request id and cannot share Rei's transaction, so a crash in between leaves a row with no task: after a restart it ends `unknown_after_restart` and is never retried automatically, because the task may have started and a second one would cost a second summary. Running `/compact` again uses a new request id.
- Barrier, enforced by the server: `/compact` is refused with `409 busy` while a run is active or queued, another compaction (manual or automatic) is running, or an earlier request is unresolved. While one is open, a user send is refused with `409 compacting` (the composer keeps the draft and disables Send with the reason); reports and triggers wait in their outbox and are delivered when it ends. A retry of an already-admitted request is still answered.
- The composer shows a status line for accepted, running and pending placement; the compaction marker in the transcript is the record of success. Nothing is shown as compacted before it is committed. A fork is compacted on its own, not with the sessions that share its tree.

## API

- `POST /api/sessions/:id/attachments`: authenticated multipart form containing one `file`; returns `{ attachment: { id, name, mediaType, size } }`. Requires the normal `x-rei: 1` CSRF header. The request stream is bounded before multipart parsing.
- `GET /api/sessions/:id/attachments/:attachmentId`: authenticated original-byte download. A session can read its uploads and files inherited through copied messages. `?preview=1` permits inline previews only for PNG, JPEG, GIF, and WebP; other formats use the [attachment preview viewer](file-previews.md), which reads original bytes without changing download behavior. Office files render directly in the browser; the authenticated `GET /api/sessions/:id/attachments/:attachmentId/preview` endpoint remains available for explicit compatibility conversion.
- `POST /api/sessions/:id/messages`: existing `requestId` and `text`, plus optional `files: FileReference[]` and `mentions: { kind: 'chat' | 'connector', id, label, start, end }[]`. Mention offsets are UTF-16 positions into `text`, covering the exact `@label`. References must be ordered and non-overlapping. Text-only requests need no file references. At most 100 mentions are accepted.
- `POST /api/sessions/:id/messages` also accepts optional `selectedSkills: { id, version }[]` (see above).
- `POST /api/sessions/:id/edit`: optionally accepts updated `mentions` positions for retained references, and `selectedSkills` (absent keeps the original's, `[]` sends none). Attachments are inherited; editing cannot introduce a new referenced target. Legacy clients may omit mentions.
- Saved messages and SSE message events carry optional `attachments` metadata and `mentions`. Retrying the same request ID returns the original message/run IDs even if referenced resources have since disappeared.
- `read_chat({ session_id, cursor? })`: read-only policy-wrapped model tool available in every chat type. Returns up to 20 messages and 24,000 text characters per page, with message IDs, roles, timestamps, fragment offsets, and `next_cursor`. Initially reads the most recent messages; cursors retrieve older pages or subsequent fragments of a long message. Reading other-session assistant/report content carries the source session’s taint.

## Storage and execution

Limits are 1 GiB per file, 10 files and 2 GiB per message. Uploads and downloads are streamed, and a large file reaches the model only through bounded reads (see [library.md](library.md)). Any file format can be uploaded, but interpreting it depends on available sandbox tools. Image thumbnails are presentation previews, not a promise that the model supports a given file format.

Migration 21 adds attachment metadata and message attachment/mention fields. Original-byte retrieval uses the durable blob store; a unique storage envelope isolates attachment lifetime from trace-blob deduplication. Files are staged beneath `.attachments/<message-id>/` in the receiving agent’s shared sandbox workspace before model submission. The model receives original names and staged paths. Prepared model input is persisted for durable replay. Sandbox failure ends the run visibly before model submission, retaining an editable/retryable user message and its files.

Copied messages retain file references. A file referenced by any surviving message is retained even after its uploading chat is deleted. Migration 22 promotes successful uploads immediately to the persistent [Library](library.md), including files removed from a draft. They remain until Library Trash/purge and all surviving message references release ownership. Unpublished retained tool media still expires after 24 hours. Staged workspace files follow the existing agent-workspace lifetime and are purged when the agent is deleted.

Browser drafts (including original files) use IndexedDB per chat; interrupted uploads restore as retryable failures. Unconfirmed sends retain their full payload and request ID in session storage for recovery. Removing a draft file does not delete a file used by another message. Browser storage failure is surfaced for drafts and does not prevent sending.
