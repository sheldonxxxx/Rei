# Tool activity

Simple and Full modes use the same activity group and row components: a short label, static tool icon and status. Rows are open while the run is working and collapse under “Worked for …” when it completes. Failed and blocked calls remain expanded by default; running, stopped, failed and approval states come from recorded execution status. The user can expand or collapse the group at any time (expanding downward beneath the summary without jumping to the bottom), and changing modes preserves that choice.

The group's heading says how the run ended, with its time: “Worked for 4.0 s”, “Failed after 2 min 34 s”, “Stopped after 5 s”. A failed run the user went on from with Continue reads “Interrupted after 2 min 34 s” instead: the Continue run has its own group and its own result, so the earlier failure is no longer the outcome (the trace marks it `continued`). Both groups sit under the message that was being answered, and Inspect on the reply opens the latest run. Its failed step stays marked when the group opens.

A call that Pi reports as parked (live status `sleeping` or `waiting`) reads “Waiting”, or “Waiting for approval” when it asked for one, never “Running”. While a run's only work is parked, its group heading reads “Waiting…”. A parked call holds no work and resumes when what it waits for arrives. A browser call made while the user controls the window parks the same way, however long they take, and runs once when the takeover ends or is cancelled; it asks for no approval until then.

In Simple mode, a working run shows only its latest five rows. Expanding the group by hand while it works shows every row, and the group collapses again when the run completes, even if the user had expanded it during the run.

Full mode adds model calls, step counts, side-effect counts, and Knowledge page and web source chips. Each row shows its tool/model name, policy decision, tokens and timing as applicable beneath the activity description, and opens Inspect when clicked. Inspect uses the same row descriptions, icons and status styling, and the same description as the tool detail title. Simple mode shows only quiet one-line tool activity without badges. Execution payloads load only when Inspect opens a step.

Every policy-managed tool accepts an optional top-level `_activity` string. The `tool_activity` prompt section asks the model for a few words in the user's language describing the call, without secrets or claims of success. Labels are normalized to one line, limited to 120 characters and rendered as plain text. Calls without a label, including historical calls, fall back to the existing policy summary or tool name.

`_activity` is removed before policy inspection, approval hashing, previews and execution, including MCP dispatch. It cannot replace the tool-owned approval summary. It is stored separately as `steps.activity` and is removed with the rest of the trace when its chat is deleted.

The chat uses the existing paginated trace summary API, refreshed on message/run changes and polled every three seconds while a run is active. It does not fetch tool input/output or provider payloads for this display. “Load earlier activity” loads older runs.

`search_capabilities` is an ordinary tool row; its label is the model's `_activity` or the search summary. A run that sees connector tools change gets a **Capabilities changed** row (puzzle icon) with no input or output. In Full mode the Trace shows what a search ranked and loaded, and each model call's offered tools ([capability-discovery.md](capability-discovery.md)).

## Scripts (Code mode)

How code mode works, who may call what and how approvals behave inside a script are in [code-mode.md](code-mode.md). This section is what the chat and Trace show.

A `codemode` call is one row: a code icon, the model's `_activity` (else "Ran a script"; never the first line of code) and "· N calls" once it has made any, or has finished. Its status reads like other rows, with two waiting states from its nested calls: **Waiting for approval** while one waits on a decision, **Waiting** while another is parked. The run's heading follows ("Waiting for approval", "Waiting…").

- **Simple mode** shows only that row. Its calls are hidden and the "latest five rows" count the script as one.
- **Full mode** adds a chevron beside the row that shows the calls, indented under it, in the order they were made, each with its usual icon, label, policy decision and timing, and opening its own Inspect. The calls open while the script works and stay as they were when it ends, so nothing moves; a script already finished when the chat opens starts folded.
- **Where the rows come from.** Trace steps group under their script by `StepSummary.parentStepId`. A call the live run has (`LiveTool.parentCallId` = the script's call id) but the trace has not recorded yet (the trace is fetched every few seconds) shows as a stand-in row, disabled, with the key the recorded step will have (the call's id). When the trace catches up the same row takes the step's label and becomes openable, so there is no flicker.
- **Inspect** on the script step shows, in this order: the code (highlighted, line-numbered, with Copy), the output, then the calls (`tool.script.calls`: name, arguments, status, time, error; each opens its own step when the trace has it). When Pi cut the output, a note says the model saw a shortened copy and gives the saved path; this is read from the output text, since the server does not keep Pi's `fullOutputPath`. A script refused before it ran has no calls list and shows its recorded input.
- **Approval cards.** An approval whose `parentCallId` is the script's call id is drawn under the script's row, in both modes, whether or not its calls are folded, and carries "Asked by a script" (Details lists it as "Asked by"). It is not repeated in the transcript. If the row is not drawn (the group is folded, the row is among the older ones in Simple mode, or the run is not loaded) the card sits below the activity instead; a card whose script is in no loaded trace, such as the parent-chat mirror of a spawned chat, keeps its usual place. When the script ended before the user decided, the card is cancelled and says "The script that asked for this ended" (`cancelReason: "script_ended"`).
- **Waiting and ending.** While a nested call is parked on a card, the script's row and the run read "Waiting for approval", and the card is how to move it. After a denial the call rejects in the script with the denial text ("Approval #N was denied…"), and the script goes on or fails with it. When Stop or the deadline ends the script first, the parked call is aborted and its card is withdrawn with the reason. In a trigger session, a nested call that asks is blocked at once ("needs the user's approval (#N)"), and the script ends with that error.
- **Fenced output.** When a nested call read the web or a connector, the script's output reaches the model, and so Inspect, between `page-content` markers that name the source tools. The recorded output equals what the model got.
- **Totals.** The Trace counts nested calls in the run's tool calls, with the script as one more. The context breakdown shows one tool call and one result for a script, since nested outputs never enter the model's context.
